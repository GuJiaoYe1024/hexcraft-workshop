# 内容管线手册

对应规范：22-内容管线与数据驱动、19-存档迁移与数据安全、17-本地化与翻译规范。
本手册的每条结论都来自实际代码与实检，不是设计意图。

---

## 1. 三类内容 JSON 一览

| 类型 | 目录 | 事件字段名 | ID 来源 | schema |
|---|---|---|---|---|
| 海克斯 | `data/hexworkshop/hextech/` | `event` | 文件名去 `.json` | `docs/schema/hextech.schema.json` |
| 装备 | `data/hexworkshop/equipment/` | `event` | 文件名去 `.json` | `docs/schema/equipment.schema.json` |
| 世界海克斯 | `data/hexworkshop/world_hexes/` | **`effect`** | 文件名去 `.json` | `docs/schema/world_hex.schema.json` |

三个要点，都很容易踩：

1. **JSON 里没有 `id` 字段**。774 个海克斯全部靠文件名做 ID，重命名文件等于换 ID，玩家已拥有的记录会对不上。
2. **世界海克斯用 `effect` 而不是 `event`**。写错字段不会报错，只是这条内容静默无效果。
3. **`rarity` 大小写不统一但能混用**。海克斯/装备写大写 `SILVER`/`GOLD`/`PRISMATIC`，世界海克斯现存 4 条写小写。`HextechRarity.byKey` 用 `equalsIgnoreCase` 比较，两种都认。新增内容统一写大写。

存量规模（2026-11-14 实测）：hextech 774 / equipment 61 / world_hexes 4。

## 2. 两个最容易读错的字段

| 字段 | 实际含义 | 容易被误读成 |
|---|---|---|
| `mods` | **属性修饰**：`[{"attr":"max_health","perLevel":50}]`，每级加什么属性 | 「依赖哪些模组」 |
| `source` | **归属/依赖标记**：`tacz` / `irons_spellbooks` / `dlc_niyuan` 等 | 「来源说明文字」 |

`mods` 在 hextech 里出现 318 次，和「模组」毫无关系。
`source` 才是真依赖：`HextechRegistry.isSourceEnabled` 里有 `if (!ModList.get().isLoaded(modid)) return false;`，目标 mod 没装就不进抽取池。

**不改名**——835 个 JSON、加载器、全部脚本都要跟着动，风险远大于收益。

`mods.attr` 只认简写：`armor` / `attack_damage` / `attack_knockback` / `attack_speed` / `knockback_resistance` / `luck` / `max_health` / `movement_speed` / `tough`。写全名不会生效。

## 3. 加载前静态校验

```powershell
python H:\MC1314\MOD\build\validate_schema.py
```

这个脚本**不含自己的规则**，规则全部从 `docs/schema/*.schema.json` 读，所以 schema 改了脚本自动跟着变，不会漂移。它检查：必填字段、类型、枚举、正则、数值范围、未声明字段、UTF-8 BOM。

当前基线（2026-11-14）：839 个文件、0 不合格、0 BOM。

标准做法是每次大批量改 JSON 后跑一遍，五步顺序：**BOM → 语法 → 必填 → 枚举/范围 → ID 唯一**。`build/` 下已有 `check_json.py`（语法 + ID 唯一）、`check_token.py`（token 是否真有实现）、`check_hex_shape.py`（形态是否有效），与本脚本互补。

## 4. 热重载边界表

### 4.1 机制

| 命令 | 实际调用链 | 重载范围 |
|---|---|---|
| `/hexcraft reload` | `server.reloadResources(emptyList())` → `SimpleJsonResourceReloadListener` | 服务端数据包目录下的 `data/hexworkshop/**`（`HexDataLoader` / `EquipmentDataLoader` / `WorldHexDataLoader` 全部重新 apply） |
| `/hexcraft reload dlc` | `DlcManager.reloadDlc()` → `scan()` + `applyHexPacks()` + `applyEquipPacks()` + `applyWorldHexPacks()` | `hexworkshop_dlc/packs/` 下全部外接包 |
| 配置保存/改动 | `Hexcraft` 的配置 `Reloading`/`Loading` 事件 → `HextechRegistry.invalidatePoolCache()` | 只清抽取池缓存，不重读内容 |

### 4.2 能热更的

| 改动 | 用哪条命令 | 备注 |
|---|---|---|
| 已有内容的 `rarity` / `weight` / `event` / `mods` / `category` / `theme` / `stackTag` / `stack` 数值 | `/hexcraft reload` | 抽取池缓存会失效重建 |
| 新增一条内容 JSON（新 ID） | `/hexcraft reload` | 新 ID 直接进池；但玩家已有存档里不会自动获得 |
| 删除一条内容 JSON | `/hexcraft reload` | 已拥有的玩家记录保留，只是不再抽取 |
| DLC 包启停 / 新增 / 删除包 | `/hexcraft reload dlc` | 依赖环会在扫描阶段被拦下 |
| 配置项数值 | 配置界面保存 | 清池缓存即时生效 |
| 权重、保底、价格、叠层上限等全部 `HexConfig` 项 | 同上 | 无需重启 |

### 4.3 必须重启的

| 改动 | 为什么 | 正确做法 |
|---|---|---|
| 新增 Java 侧 token 实现 | token 表在类初始化时建好，reload 不会重建 | 重启服务端 |
| 新增物品 / 方块 / 实体 / 粒子 / 属性 | 注册表在启动期冻结，运行期无法追加 | 重启（客户端 + 服务端） |
| 新增 / 修改配置项 | `ForgeConfigSpec` 在 `<clinit>` 里 build | 重启服务端 |
| lang 文案（`zh_cn.json` / `en_us.json`） | 是客户端资源包，服务端 `/reload` 不碰客户端 | 客户端 F3+T 重载资源，或重开客户端 |
| `modId`、包名、`PacketHandler.VERSION` | 影响存档键名与联机握手 | 必须重启，且要同时更新客户端 jar |

### 4.4 一个容易忽略的坑

`/reload` 之后**不要只看 `/datapack list` 显示「已加载」**就以为成功了——Mojang 侧有静默失败的已知 bug（`MC-135501`：无效 tag 引用会中止后续加载，但列表仍显示已加载）。判断标准只有一个：**日志里有没有 ERROR**。

本项目的 loader 会在 apply 末尾打 `loaded N hextech definition(s) from datapack (M failed)`，直接看 `M` 是不是 0。

## 5. DLC 数据契约

### 5.1 目录与 ID

```
hexworkshop_dlc/
├── dlc_index.json          # 启用状态，由模组自动维护，玩家不要手改
└── packs/
    ├── my_pack/            # 文件夹形式，ID = 目录名
    │   ├── dlc_meta.json
    │   └── data/
    │       ├── hex/*.json
    │       ├── equipment/*.json
    │       └── world_hex/*.json
    └── my_pack.zip         # 压缩包形式，ID = 完整文件名（含 .zip）
        ├── dlc_meta.json   # 必须在压缩包根目录
        └── data/...
```

**ID 规则**（`DlcManager` 实读）：

- 文件夹形式：`info.id = 目录名`
- zip 形式：`info.id = 完整文件名`（**包含 `.zip` 后缀**，不是去后缀的裸名）

两种形式的 ID 不一样，混用会导致依赖声明对不上。

### 5.2 `dlc_meta.json` 字段

| 字段 | 必填 | 类型 | 缺省 | 说明 |
|---|---|---|---|---|
| `name` | 否 | string | 同 ID | 界面显示名 |
| `description` | 否 | string | 空串 | 界面介绍文字 |
| `version` | 否 | string | `"1.0.0"` | 目前**仅记录不校验**，版本不匹配不会降级也不会拒绝加载 |
| `dependencies` | 否 | string[] | 空 | 依赖的其他包 ID。成环会被拦下（见 5.4） |
| `isCodeDlc` | 否 | boolean | `false` | true 表示这是代码 DLC，不参与纯数据合并 |

**未知字段会被忽略**，不报错。所以写错字段名不会有提示，只是不生效。

### 5.3 内容目录

| 目录 | 对应类型 |
|---|---|
| `data/hex/` | 海克斯 |
| `data/equipment/` | 装备 |
| `data/world_hex/` | 世界海克斯 |

三条限制：

1. **只读子目录第一层 JSON**（`readPackJson` 里 `if (id.contains("/")) continue;`），嵌套子目录会被跳过。
2. **文件名即内容 ID**，与内置内容同规则。和内置内容或别的包撞 ID 会覆盖，后加载者赢。
3. 字段语法与内置完全一致，见第 1 节三份 schema。

### 5.4 降级与拒绝加载

| 情况 | 后果 |
|---|---|
| 缺 `dlc_meta.json` | `error = "无效DLC，缺少 dlc_meta.json"`，不加载 |
| zip 根目录没有 `dlc_meta.json` | `error = "无效DLC，压缩包内部结构错误"`，不加载 |
| zip 打不开 | `error = "压缩包无法读取"`，不加载 |
| `dlc_meta.json` 解析失败 | `error = "dlc_meta.json 解析失败"`，不加载 |
| **依赖成环**（a→b→a） | `error = "依赖成环：a → b → a"`，不加载。**环外的包不受影响** |
| 依赖指向未安装的包 | **不报警、不拒绝**，按正常包加载 |
| `version` 与当前版本不符 | **没有任何反应**，照常加载 |

最后两条是现状：依赖缺失不强制、版本不校验。写契约时如实标出，不假装有。

`activeDataPacks()` 只取 `enabled && !isCodeDlc && error.isEmpty()` 的包，`packEnabledOf()` 同样要求 `error.isEmpty()`——所以上面每种失败都自动把该包从抽取池摘掉，不需要额外代码。

### 5.5 新增包的默认状态

新包**默认不启用**（`index.getOrDefault(id, false)`）。玩家需要在 DLC 界面手动开启，或让模组在 `dlc_index.json` 里写 `true`。这是刻意设计——防止玩家丢一个包进来就立刻改变抽取池。

## 6. 变更纪律

改一批数值时：

1. **先备份**：整个数据目录复制一份带时间戳
2. **用脚本改，不用正则拍**：正则改 JSON 很容易误伤，用 JSON 解析器读改写
3. **改完跑 `validate_schema.py`**
4. **抽查 3~5 个**看改对了没
5. **记进 CHANGELOG**：改了多少条、按什么规则改

## 7. 检查清单

- [ ] 新 JSON 有没有 BOM
- [ ] 必填字段齐了吗（`validate_schema.py`）
- [ ] 文件名（即 ID）唯一吗（`check_json.py`）
- [ ] `event` 里的 token 在 Java 侧真有实现吗（`check_token.py`）
- [ ] 这次改动能热重载，还是必须重启（第 4 节）
- [ ] `/reload` 后日志里 `loaded N` 的失败数是不是 0（别看 `/datapack list`）
- [ ] 批量改数值前备份了吗
- [ ] DLC 包的 `dependencies` 有没有成环（日志里搜「依赖成环」）
