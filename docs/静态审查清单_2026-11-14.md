## 三、待处理清单（按优先级）

### P1 服务端每 tick 全量效果汇总（性能）

- 位置：`HextechEvents.onTick`（约 2476 行）
- 现象：每个在线玩家**每 tick** 调一次 `effectBatch(data, TICK_EFFECT_KEYS)`，内部遍历该玩家全部海克斯（有效 749 条）+ 49 条羁绊。10 人服 = 每 tick 约 8000 次键比对。
- 建议：按玩家数据版本号做 tick 级缓存，或把 `effectBatch` 降频到每 2~4 tick（现有 TACZ 段已按 `tickCount % 4` 分段，说明降频对判定无感知）。
- 影响：纯性能，不改数值与手感。
- **状态：已修（v0.9.24）** —— 新增 `TOKEN_VALUE_CACHE`，token 数值按 token 字符串缓存，只解析一次，后续查表；`effectBatch` 与单键 `effect` 共用。

### P2 客户端属性页 60 次单键汇总（性能）

- 位置：`HextechPageScreen.collectHiddenRows`（约 769-788 行）
- 现象：`EFFECT_KEYS` 与 `TACZ_KEYS` 的每一项各调一次 `HextechEvents.effect()`，注释自述「约 60 个键 × 48 条羁绊」。虽然有 250ms 缓存，但每次刷新仍是一次全量 × 60。
- 建议：服务端已有 `effectBatch(data, keys)`，客户端改调一次批量版，把 60 次全量降到 1 次。
- 影响：纯性能，界面表现不变。
- **状态：已修（v0.9.24）** —— 新增客户端批量重载 `effectBatch(List<HexEntry>, Collection<String>)`，口径与单键版一致（海克斯 + 羁绊，不含装备）；属性页由约 50 次全量遍历降为 1 次。

### P3 驯服生物回血分配不均（逻辑缺陷）

- 位置：`WorldHexEvents.onLivingTick`（约 408-419 行）
- 现象：用**全类静态计数器** `if ((++TICK & 15) != 0) return;` 做低频过滤。所有驯服生物共用 `TICK`，意味着每 16 次调用只有 1 次通过，而不是「每只生物每 16 tick 一次」。驯服生物一多，单只被治疗的频率被稀释，且分布不固定。
- 建议：改用实体自身的 `e.tickCount % 16 == 0`，让每只生物独立按 0.8s 节奏回血。
- 影响：会改变治疗频率（变均匀），属于行为修正，需要你确认是否要改。
- **状态：已修（v0.9.24，已确认）** —— 改为 `e.tickCount % 16 == 0`，删除全局静态 `TICK`，每只驯服生物各自按 0.8s 稳定结算。

### P4 Clone 口径不统一（一致性）

- 位置：`WorldHexEvents.onPlayerClone`（约 430 行）
- 现象：同 `HextechEvents.onClone` 一样监听 `PlayerEvent.Clone`，但不判 `isWasDeath()`。世界海克斯 modifier 是重算，重复应用无害，所以目前不出问题；但与 `HextechEvents` 的新口径不一致，后续维护容易踩。
- 建议：加注释说明「此处为幂等重算、无需区分死亡/末地返回」，或加同样判定。
- 影响：无功能变化。

### P5 deprecated API 4 处（代码卫生）

| 位置 | 旧 API | 建议 |
|---|---|---|
| `ModCapabilities:20` | `new ResourceLocation(String,String)` | 改 `ResourceLocation.fromNamespaceAndPath` |
| `HextechEvents:3003` | 同上 | 同上 |
| `PacketHandler:14` | 同上 | 同上 |
| `Hexcraft:34` | `FMLJavaModLoadingContext.get().getModEventBus()` | 改构造函数注入 `IEventBus` |
| `Hexcraft:43` / `:44` | `ModLoadingContext.get().registerConfig(...)` | 改构造函数注入 `ModContainer` |

- 影响：不改功能，仅消除编译警告。

### P6 羁绊成员 id 无校验（健壮性）

- 位置：`ComboRegistry.java`（509 处 id 字面量）
- 现象：羁绊成员表全部是硬编码字符串，成员 id 拼错不会有编译错误，也不会在运行期报错——只是那一件永远不计入档位，玩家看到「凑齐了却不激活」。
- 建议：在 `HextechRegistry` 加载完成后加一次启动期校验：遍历所有羁绊成员，若 `HextechRegistry.get(id) == null` 就打 WARN 并把该 id 列出来。
- 影响：只增加启动日志，不改玩法。

## 四、脚本误报说明（不需要处理）

`audit_hardcoded_ids.py` 报「数据中不存在的引用 27 个」，逐条核对后确认**全部是误报**，共三类：

1. **效果键**：`equip_power`、`equip_count_atk/armor/hp`、`hex_coin`、`hex_power`、`hex_slot_boost` —— 这些是 `event`/`effect` 键，不是数据文件名。
2. **persistentData 标记键**：`hex_frost`、`hex_split_child` —— 实体 NBT 布尔标记，本来就不该有数据文件。
3. **动态前缀**：`hex_ac_`、`hex_blade_`、`hex_goety_`、`hex_irons_`、`hex_tacz_`、`equip_tf_` 等 —— 代码里拼 `前缀 + 变量` 的字符串片段，正则把它们当成完整 id 抓了出来。

同一脚本报的 lang 缺失项（`hexcraft.hextech.`、`hexcraft.gui.tab.` 等）也是动态前缀误报，`_lang_check.py` 已确认中英集合一致。
